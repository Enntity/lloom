## Selected starting configuration

Two GB10 Sparks, TP2 over private IPv4 RoCE-v2, worker first. Main routed
experts retain NVIDIA NVFP4; MTP experts retain block FP8; PLE retains per-tensor
FP8. The MTP overlay handles local draft layer numbering and mixed quant dispatch.
The disk reader fetches original PLE rows from each rank's local NVMe and leaves
the model's scale/dequantization in place. No checkpoint rewrite is performed.

FP8 E4M3 KV, native 262144 context, piecewise CUDA graphs, maximum eight engine
sequences, batch budget 8192, initial GPU utilization 0.75, and three speculative
tokens. Initial LLooM admission is four active plus eight queued. Thinking is
enabled with low reasoning effort; tools use `qwen3_xml`.

Prefix caching remains disabled pending hybrid-cache correctness fixes. Native
context is retained rather than interpreting a million-token retrieval pass as
general long-context quality. Reduced vocabulary and NVFP4 KV remain unselected.

## Rollout and rollback

Recipe v4 is archived, and its backend assets are untouched. The NVIDIA lane
uses new container names and an independently mounted, hashed patch directory.
Only Qwen recipe assets and derived Qwen configuration entries are deployed;
unrelated gateway source changes in the working tree are excluded.

DS4FV local routing was suspended temporarily so new Runtime requests could use
its existing cloud fallback. Active local requests drained to zero before the
keep-warm pin was released. Managed lifecycle stopped both old ranks; neither
container reported an OOM kill. Private config backups are retained on each host.
The stable Qwen alias was suspended locally during canaries; `q38fn-local`
provided strict local attribution. Final promotion resumed the local member on
the leader gateway, with `qwen3.8-flash-next` first and `cloud/openrouter/q38fn`
second. Authenticated synthetic requests verified both the suspended-local cloud
branch and, after promotion, the normal local branch. The worker is a physical
rank, not the public cloud-routing gateway; its local alias remains suspended.

## Rejected newer-nightly comparison and recovery

A separate `e962733e` candidate retained the newer native QSA kernels with BF16
KV and GPU-resident FP8 PLE, plus source-guarded PLE/MTP loader fixes. Both hosts
became unreachable around 18:48 UTC during compilation. Previous-boot logs on
both hosts contain repeated NVIDIA `NV_ERR_NO_MEMORY` allocation failures at that
time. This establishes memory pressure during the failure, but does not isolate
one kernel or prove an upstream recipe alone caused it. No semantic gate passed.
The user power-cycled both hosts; recovery restored the tested `8a728663` entries
and explicitly stopped and disabled restart on both experimental containers.

DeepSeek was not co-resident: active/queued local requests drained to zero,
then managed lifecycle stopped the head at 18:07:30 UTC and worker at 18:07:44 UTC.
Both Sparks had about 116 GiB MemAvailable before Qwen admission. Qwen's first
admission was after 18:16 UTC. The newer comparison began only after the tested
Qwen variant drained to zero and stopped.

During recovery, the user explicitly requested suspension of competing large
models. On both hosts their runtime `enabled` and `keepWarm` flags are false,
and affected alias members are suspended. Private before-isolation backups are
retained. Qwen is the sole enabled large runtime, with a host-specific keep-warm
pin; the portable recipe default remains on-demand. Cloud routes remain available.
Other large models must be explicitly re-enabled before future local use.

MTP3 remains selected. MTP2 and MTP4 have not been compared on this pair in this
rollout; upstream headline rates are not accepted as local measurements. The
rejected newer candidate is retained only as clearly marked source provenance.
Do not call this the universally fastest Qwen stack or evidence of GLM parity.

Post-recovery smoke: all five checks passed again through `q38fn-local`, including
vision and structured tools, with exact local gateway attribution. A premature
probe during startup received the expected `RUNTIME_STARTING` 429; it did not
start a second model or enter the accepted inference results.

Recovery qualification: NVIDIA allocation warnings also occurred on the restored
stack while the hosts remained reachable. These logs alone do not isolate the
freeze cause. The newer candidate is rejected because it lost both hosts and
never passed inference gates; the selected configuration must pass live requests
and clean drain after recovery.


## Final recovery gates

All 12 mixed/repeated structured-tool requests passed after reboot. Six callers
exercised four active slots and two queued; monitoring observed 72 samples and
both gateway and raw vLLM returned to zero running/waiting requests. The largest
input was again 46,910 tokens: 25.580 s TTFT and 38.943 s total in this run.
A fresh public `q38fn` canary returned exact `Q38_ROUTE_OK`, HTTP 200, attributed
to `qwen3.8-flash-next` / `qwen38-flash-next`. Both hosts remained reachable,
containers stayed running, and final MemAvailable was about 14 GiB head / 17 GiB
worker, with 4.8 / 2.9 GiB swap used. Qwen remains pinned; competing large local
models remain disabled/suspended per the user's instruction.

All selected backend files match the checkout on both hosts. Their installed
recipe indexes select v5 and retain archived v4. Recipe guard tests, focused ESLint,
interchange validation, package installation smoke (578 files), and diff checks
passed. Deployment contains only scoped recipe/backend assets and derived config;
unrelated gateway source was not packaged or deployed by this task. The portable recipe, backend assets and synthetic evidence are now included in the public release.
